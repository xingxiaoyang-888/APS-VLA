# 正式下游作业入口（E04）

本入口只规划和登记 `formal_main_v2` 的 development / final / collect / full / components 作业。训练路径、173 个冻结文件、既有适配器、策略、环境、trial 循环及计时范围均不修改。实现阶段仅做项目内 CPU 合成测试；不代表已运行闭环、测速或已具备真实下游审计收据。

## 文件与身份

- root 入口：`scripts/ops/formal_downstream_supervisor.py`。
- 服务器 wrapper：`scripts/server/run_formal_downstream.py`。
- 继续调用 `scripts/ops/formal_evaluation_adapter.py`，固定 SHA256 为 `260f1525455ef00e74edc1b53f913a7fc955d06c5f4905794e640c1ff7798e5e`。
- 固定 source inventory：`results/formal_main_v2/source/formal_main_v2_run_564be0995e.json`，173 文件集合 SHA256 为 `dd3e5450e80b8e1f05a78acf6a05daf393f7362420fd8e87a8e6f5ec03feb61e`。
- 每份 invocation 另外绑定 controller / wrapper 自身 SHA、执行清单、全部运行输入与 root 审计文件 SHA。它不要求当前 Git HEAD 等于旧 snapshot commit。

## 两步调用

先运行只读 `plan`，检查输出及 `plan_sha256`；它不联网、不写监督状态、不读 checkpoint 或封存初态值。例如：

```powershell
python -B scripts/ops/formal_downstream_supervisor.py plan --stage development --execution-manifest results/formal_main_v2/execution/libero_10_development_references_v1.json --stop-after 10
```

只有 root 显式执行同参数的 `submit --root-submit --expected-plan-sha256 <已检查的值>` 才会联网。该操作持有原监督状态锁，仅刷新已登记的正式作业，然后重新规划；证据改变使计划 SHA 改变并拒绝提交。上传采用校验后独占发布，已有不同 SHA 文件拒绝覆盖。登记 invocation 和 pending 后最多调用一次 `sbatch`；上传失败、超时或 sbatch 返回不明确均保留 pending，禁止自动重提。

复用原 L40 资源设置：1 GPU、7 CPU、64 GiB、4 小时、`--no-requeue`，完整 Slurm 分配时长计入成本。新的 wrapper 明确允许上述 adapter；它不修改旧 `run_formal_stage.py` 的入口白名单。

## 续跑与失败

同套件、stage、方法的已有 active / unknown 作业阻止新提交；方法分组相交也拒绝，避免重复 trial。已科学完成的阶段不可再跑。Slurm `CANCELLED by ...`、`TIMEOUT+` 等按现有 puller 规范识别，原始状态和完整分配成本仍保留。

闭环续跑必须显式 `--resume --prior-review <最近终态 root 审计>`，使用同一目录、manifest、config、panel、run signature 和完整原始 ledger。终态 trial 不重跑；未完成 start 保留并记录未知成本。SHA 回存必须前后清单一致、作业终态、每个文件校验通过；所有 prior allocation 都有成本。缺 ledger、坏 JSON 或缺末尾换行直接拒绝，原字节不修复、不截断。当前入口另要求最新 closed-loop report 与 raw ledger 终态数一致；若报告落后，先交 root 审核，不自动改写历史报告。

若已有失败作业，还须 `--repair-record`。记录格式为 `schema=formal_main_v2, kind=downstream_repair, status=reviewed, reviewed_by=root`，绑定 `stage_key`、全部 `failed_job_ids`、`target_source_sha256`、`adapter_sha256`、`execution_manifest_sha256`、`prior_review_sha256`，以及非空 `diagnosis` / `bounded_fix`。不得借修复改变科学设置。

profile 不续写旧计时目录；失败后需同样保留终态回存、root review 和 repair，使用新的 attempt 目录。wrapper 只复制本 job 精确命名的 adapter JSON / JSONL 原字节到 run_root 内，逐项绑定原路径、SHA 和字节数；不混拷其他作业目录。失败和不完整 journal 保留，全部账单继续累计。

**已知待人工处理边界：**若作业在建立 ledger 或适配器收据前失败，当前严格续跑不能直接处理。入口不自动重跑；root 必须另行判定是否零 trial，保留失败日志/账单，再决定有界修复或新目录。当前没有自动修复 producer。

## 下游 root 审计收据契约

本入口只消费以下收据并重新核对 SHA；尚无实际下游审计 producer。root 后续须审查真实终态证据后生成，不能把此契约或合成测试当真实 `passed`。

共同字段：`schema=formal_main_v2, kind=root_downstream_review, status=passed, reviewed_by=root`，以及 `job_id, stage, stage_key, source_sha256, adapter_sha256, invocation_sha256, run_root, execution_manifest_sha256, terminal_status, exit_code, scientific_complete, pull_receipt, files`。

- `pull_receipt` 指向 `results/formal_main_v2/pulls/.../receipt.json`，必须为稳定终态的 `verified_nonweight_snapshot`，不含权重或最终 state-value panel。
- `files` 为完整 run_root 非权重输出、job receipt、Slurm out/err 的项目相对路径→SHA256；必须含该 job 的 adapter 归档。wrapper receipt 中每项归档来源、字节数与 pull 一致。
- 闭环还需 `run_signature, completed_trials, unfinished_attempts_unknown_cost`，逐项与原 ledger 复核；所有 ledger invocation 的 job 必须登记，终态 cost 保留。
- `scientific_complete=true` 只能用于 `COMPLETED/0:0` 且科学产物实际完整的阶段。分段或失败作业可审计为证据完整的 `passed`，但必须为 `scientific_complete=false`。
- 训练门槛使用现有 segment review 的稳定 `files`。完整 `evidence_sha256` 中历史监督状态等可变文件保留原哈希，不要求之后的当前状态字节不变。

服务器先检查登记 SHA，再通过适配器重复原验收、环境及 checkpoint 检查。此 CPU 入口未验证实际 Slurm 调用、服务器支持文件发布或真实下游恢复；root 完成独立审计和真实前置条件后才可调用。
