3. `review_formal_segment_startup.py`：未来恢复作业真正完成后，原逐样本/验证/成本审计仍执行。失败 metadata scope 单列 `startup_failure_history`，成功 scope 留在原 history，全部作业账单相加。当前失败本身不产生普通 segment passed。
4. `formal_asset_downstream_review_startup.py`：未来完整5000来源审核重建 typed 失败证明，成功 metadata scopes 与失败证明精确分区，完整 allocations 及费用不变。未完成5000照常拒绝。

## 新证明与不可变字节

`startup_failure_evidence.create_candidate(project, job_id, new_bundle_relative)` 重建真实 pull、failed job receipt、stderr、失败 JSON、Object 8事件还原、服务器路径证明与173源码，复制全部实际读取的非权重原始字节到新 bundle。Spatial 原1000 progress 会在合法续跑后改变，未来复核使用这份旧字节 bundle；失败日志/receipt/compatibility 原件仍须当前 SHA 与 bundle 相同。

候选 proof 为 `kind=startup_failure_review, status=verified_startup_failure`，从不表示训练段完成。root 审核后才能将原字节发布到明确 canonical 路径：

`results/formal_main_v2/<suite>/k<budget>/seed23/training/startup_failure_reviews/<failed_job>.json`

bundle 路径亦需一并保存并纳入 Git 非权重交付。没有 bundle、篡改 SHA、出现初始化/更新、变更 checkpoint、漏账或未知失败均拒绝。proof 的 `root_recovery_authorization` 保持待定说明；真正恢复授权由另一份 root repair record 明确给出。

repair record 必须用自身完整 JSON 字节 SHA 作为文件名，绑定 stage/source、全部 failed IDs、同一原目标、canonical proof SHA、五份候选实现的 `recovery_implementation` SHA、`automatic_retry=false`、`new_attempt_limit=1`，Object 另绑定原 metadata 合同。原 invocation 的 `repair_record` 路径因此绑定内容；不改原 runner argv 结构。

## 恢复语义与后续边界

两类均显式 `--resume`。冻结 `train_formal_arm` 在 resume 文件不存在、checkpoint 目录无既有候选时记录 `resumed=false` 并从0初始化；已有候选却缺 resume 时拒绝。Spatial 必须加载原 AdamW/RNG/cursor8000，不能重新初始化。CPU 测试只用临时合成张量/小调度验证该实际核心分支，不声称已经执行真实5000或GPU恢复。

本 gateway 只补齐原失败目标，不自动继续下一段。补齐后 root 仍需普通段审核＋独审；后续段因历史 FAILED 保留，原 dispatcher 继续要求新的目标绑定 repair record。旧 `fill_reviewed_pair_slot.py` 未接该参数，不能直接用于这些 pair；root 应显式调用新 dispatcher 并保留 typed history，或另做最小 root 路由接入。当前候选不掩盖这一未接入项。
